# Пакет app

Пакет содержит HTTP-каркас, конфигурацию, SQLite v1 и адаптер классификации DeepSeek.
`ShopAssistant` выбирает серверную историю и формирует ответ только по регламенту.

| Файл | Ответственность и публичный интерфейс |
| --- | --- |
| `__init__.py` | Обозначает Python-пакет; не запускает приложение |
| `config.py` | `Settings` загружает типизированные настройки из окружения и `.env`; `load_settings()` возвращает их либо возбуждает `ConfigurationError` с именами некорректных полей без значений |
| `schemas.py` | `HealthResponse` для `/health`, `ContextMessage`, строгий `ClassificationResult` и семь типов тем |
| `main.py` | `create_app()` создаёт FastAPI; `app` — экземпляр для Uvicorn; startup проверяет настройки, инициализирует SQLite, очищает истёкшие диалоги и сохраняет настройки в `app.state.settings` |
| `assistant.py` | `ShopAssistant.respond()` проверяет сессию, выбирает контекст, сохраняет запрос, вызывает классификацию и формирует/сохраняет ответ по SQLite |
| `llm.py` | `DeepSeekClassifier.classify()` вызывает DeepSeek, проверяет JSON, ограничивает таймаут и число попыток |
| `database.py` | Соединения, SQLite v1, проверка исходного регламента, три репозитория и типизированные результаты чтения |

Сценарий `assistant.py` реализован по карточке формирования ответов.
Он ещё не подключён к HTTP-маршруту чата; API вызывает его в следующем этапе.

Зависимости: `main.py` использует `config.py`, `database.py` и `schemas.py`. Модель ответа
не зависит от конфигурации. Настройки не зависят от HTTP API. При импорте
`app.main` настройки ещё не читаются: проверка выполняется в lifespan до
обслуживания запросов. Настройки и SQLite проверяются до запуска API; ошибки
останавливают старт. Операции SQLite при старте выполняются в пуле потоков,
а не блокируют цикл событий. Глобального соединения с БД нет.

Поток текущего запроса: HTTP `GET /health` → маршрут → `HealthResponse` → JSON.
Настройки и секреты не включаются в ответ или OpenAPI. `create_app()` позволяет
создавать независимые приложения в тестах. На `/health` нет проверок внешних
сервисов: этот endpoint подтверждает только работоспособность процесса API.

`Settings` неизменяемый. `DEEPSEEK_API_KEY` хранится как `SecretStr`, скрывающий
ключ при обычном выводе модели. Значение можно получить явно через
`get_secret_value()`; его нельзя записывать в логи. `load_settings()` заменяет
стандартную ошибку Pydantic на безопасное сообщение. Приоритет источников и
допустимые значения перечислены в корневом README. Загрузка `.env` использует
[Pydantic Settings](https://docs.pydantic.dev/latest/concepts/pydantic_settings/).

## Сценарий консультации

`ShopAssistant(settings, classifier=None)` хранит настройки и необязательную
подмену `RequestClassifier`. Этот Protocol задаёт асинхронный
`classify(message, *, context=()) -> ClassificationResult`. По умолчанию
`DeepSeekClassifier` создаётся внутри защищённого сценария после сохранения
запроса пользователя, поэтому ошибка загрузки адаптера тоже обрабатывается безопасно.

`await assistant.respond(session_token_hash, message) -> str` принимает хеш
существующей серверной сессии и непустой текст. Для обработки используется
следующий поток:

1. В рабочем потоке открыть отдельное соединение, проверить активность сессии
   и удалить истёкшие диалоги. Прочитать предыдущие сообщения этой сессии.
2. Выбрать последние `CLASSIFIER_CONTEXT_MESSAGES` сообщений в хронологическом
   порядке (по умолчанию 5; 0 отключает чтение и передачу контекста).
3. Атомарно сохранить новый запрос и обновить активность существующим
   `append_user_message()`. Закрыть соединение.
4. Отдельно передать новый текст и выбранный контекст классификатору, без
   транзакции SQLite. Повторно проверить его результат через Pydantic.
5. В рабочем потоке открыть новое соединение, прочитать проверенный регламент,
   составить ответ и сохранить его через `append_assistant_message()` отдельной
   транзакцией. Закрыть соединение и вернуть текст.

Соединения не передаются между потоками и не хранятся в объекте ассистента.
Новый запрос не удаляется из истории при сбое провайдера; техническая ошибка
не сохраняется как обычный ответ. `respond()` возвращает точную константу
`TECHNICAL_ERROR_MESSAGE`: «Сейчас не могу обработать запрос. Попробуйте ещё раз
чуть позже» при ошибках адаптера, SQLite, проверке регламента/классификации или
невозможности продолжить сессию. Пустой текст и некорректный формат хеша
вызывают `ValueError`. Новую сессию сценарий не создаёт; это ответственность API.
Логи содержат этап и тип ошибки без её тела, ключа, токена и пользовательского текста.

Ответы собираются из Python-шаблонов по порядку тем и `requested_info`.
Смысловое распознавание и порядок определяет классификатор; соответствующее
требование включено в его промпт. Повторяющиеся общие условия не дублируются.
Если нужен вопрос, задаётся только первый короткий вопрос после понятной части;
произвольная `clarification_reason` модели покупателю не пересылается.

Цена и наличие берутся из конкретного товара SQLite. Поддерживаются полное
название без учёта регистра/лишних пробелов и однозначный конечный код из
каталога (например X1). Неизвестная модель обозначается явно; модель не
подставляется по умолчанию. Неоднозначный код или отсутствие модели требуют
уточнения. Для иных характеристик текущая схема не содержит фактов; они не
угадываются и не отменяют ответ о цене.

Ответ о заказе явно отделяет отсутствие доступа к его статусу от общих условий
доставки. Обычный возврат формулируется для товара без брака, включая вскрытый.
Если день превышает срок из SQLite, отказ относится к обычному возврату;
при неизвестном браке задаётся вопрос о неисправности. Явно заявленный брак
обрабатывается как экспертиза даже при метке `return`. Срок обычного возврата
и поступления денег не обещается для брака. При метке `defect` признак
`defective=true` ведёт к экспертизе, `null` — к вопросу о неисправности,
`false` — к правилам обычного возврата с учётом указанного дня.
Тема `discount` всегда даёт «Скидок нет»;
процент не используется в расчётах, цена сообщается только по отдельному запросу.
Даже если классификатор пропустит тему `discount`, Python не рассчитывает скидку:
при распознанном запросе цены он сообщит только цену из SQLite. Явная фраза
«Скидок нет» требует распознанной темы `discount`; полнота её распознавания
не гарантируется моделью и проверяется отдельно от запрета изменять цену.
Формы дней и рабочих дней согласуются с числом, например «1 день», «2 дня»,
«5 дней», «1 рабочий день», «2 рабочих дня».

## Классификация через DeepSeek

`DeepSeekClassifier(settings, *, transport=None, prompt_path=None)` загружает
единственный исходный `app/prompts/classifier.md` через `importlib.resources`
и добавляет JSON Schema из Pydantic. Ресурс включён в wheel и не зависит от
рабочего каталога или расположения репозитория. `prompt_path` сохраняет приоритет
для явно заданного файла, в том числе в тестах.
Пустая/недоступная инструкция вызывает `ClassificationError` до сетевого запроса.

`await classifier.classify(message, *, context=())` возвращает
`ClassificationResult`: `topics`, `needs_clarification`, `clarification_reason`.
В `topics` одновременно могут быть известные и внешние темы, в том числе
отдельные объекты одной темы для разных товаров. Детали принадлежат объекту темы.

| `type` / модель | Обязательные детали |
| --- | --- |
| `product` / `ProductTopic` | `product_name`: строка или null; обязательный непустой `requested_info` со всеми запрошенными сведениями |
| `delivery` / `DeliveryTopic` | `product_name`: строка или null |
| `order_status` / `OrderStatusTopic` | `order_number`: строка или null, с сохранением ведущих нулей |
| `return` / `ReturnTopic` | `product_name`, `return_day`: целое ≥0 или null, `opened`, `defective` |
| `defect` / `DefectTopic` | Те же детали для конкретного обращения по браку |
| `discount` / `DiscountTopic` | `product_name`, `requested_percent`: конечное число ≥0 или null |
| `out_of_scope` / `OutOfScopeTopic` | `question`: непустая формулировка неизвестной части вопроса |

В `requested_info` используются `PriceRequest(kind="price")`,
`AvailabilityRequest(kind="availability")` и
`FeatureRequest(kind="feature", name="название из вопроса")`.
Поле `name` обязательно только для характеристики и сохраняет её название,
например «шумоподавление». Значения цены, наличия или характеристики в эти
объекты не записываются. `app/assistant.py` проверяет наличие сведений в регламенте;
неизвестная характеристика остаётся вопросом о товаре и получает явный ответ
об отсутствии сведений.
Для составного вопроса сохраняются все пункты:

```json
{
  "type": "product",
  "product_name": "X1",
  "requested_info": [
    {"kind": "price"},
    {"kind": "feature", "name": "шумоподавление"}
  ]
}
```

Тема `product` без `requested_info` больше не проходит валидацию. Инструкция
содержит отдельные примеры цены, наличия, характеристики и их сочетания.

`opened` и `defective` различают true, false и null («не сказано»).
Nullable-поля обязательны: неизвестное значение явно передаётся как null.
При неясном смысле `needs_clarification=true` и требуется непустая причина;
без уточнения причина равна null. Пустой `topics` допустим только с уточнением.
Неизвестная деталь сама по себе не означает неоднозначность смысла.
Лишние поля, неизвестные темы и подмена типов запрещены. Валидная схема
не доказывает правильность понимания: бизнес-правила и факты проверяет Python.

`context` — последовательность `ContextMessage(role="user" | "assistant", content=...)`,
выбранная вызывающим серверным кодом. Адаптер не читает SQLite и не выбирает
историю. Порядок запроса: одна системная инструкция → переданный контекст →
новое сообщение пользователя. Роль system в контексте и пустые сообщения
отклоняются до сети. Команды «забудь правила» остаются данными роли user.

Запрос: `<DEEPSEEK_BASE_URL>/chat/completions`, модель из настроек,
`thinking.type=disabled`, `response_format.type=json_object`,
`temperature=0`, `max_tokens=2048`, без потока и перенаправлений.
HTTPX2-клиент создаётся на операцию и закрывается при выходе.
Общий asyncio-таймаут попытки и сетевой таймаут — из настроек, не более 30 секунд.
Всего 1–2 попытки, включая первую. Скрытых транспортных повторов нет.

Временные ошибки сети, HTTP 408/425/429/5xx и невалидный/усечённый результат
допускают один повтор при лимите 2. JSON не исправляется, ошибочный ответ не
добавляется в контекст. HTTP 401/403 сразу вызывают `AuthenticationError`;
постоянные ошибки и исчерпание попыток — `ClassificationError`.
Отмена asyncio не вызывает повтор. Невалидный ввод вызывает `ValueError`.
Ошибки и логи не содержат ключ, промпт, текст сообщения или тело ответа;
логируются только операция, номер попытки и безопасный HTTP-статус.

Пример внутри вызывающей coroutine:

```python
from app.config import load_settings
from app.llm import DeepSeekClassifier
from app.schemas import ContextMessage

classifier = DeepSeekClassifier(load_settings())
result = await classifier.classify(
    "А если я их вскрыл?",
    context=[ContextMessage(role="user", content="Можно вернуть X1?")],
)
```

Автоматические тесты классификатора в `tests/test_assistant.py` используют
`transport=httpx2.MockTransport(...)` без сети и ключа. Тесты `ShopAssistant`
в том же файле подменяют `RequestClassifier`, оставляя настоящую временную SQLite.
HTTP-маршрут и браузерный чат реализуются отдельно.

## Интерфейс слоя данных

Все компоненты размещены в существующем `database.py`, без ORM и общего
BaseRepository. Репозитории получают соединение, которое создаёт и закрывает
вызывающий код. На HTTP-запрос нужно отдельное соединение в том же рабочем потоке.

| Интерфейс | Результат и ответственность |
| --- | --- |
| `open_database(path)` | Контекст соединения с `foreign_keys=ON`, `busy_timeout=5000`; закрытие при выходе |
| `transaction(connection)` | Короткий `BEGIN IMMEDIATE` с фиксацией либо откатом; вложенные транзакции не поддерживаются |
| `initialize_database(path, ttl_hours=24, *, now=None)` | Атомарное создание v1 либо проверка существующей БД; очистка истёкших диалогов только после успешной проверки |
| `hash_session_token(token)` | SHA-256 непустого токена; исходное значение не записывается в БД |
| `KnowledgeRepository(connection).read()` | Новый `Regulation` из четырёх таблиц с проверкой всех шести исходных фактов; без кеша и подстановок |
| `ConversationRepository(connection, ttl_hours=24).create(*, now=None)` | Пара `(Conversation, token)`; UUID и высокоэнтропийный токен создаются сервером, хранится только хеш |
| `.find_active(session_token_hash, *, now=None)` | Активный `Conversation` либо `None`; точная граница TTL уже считается истечением |
| `.touch(conversation_id, *, now=None)` | Обновление активности непросроченного диалога; `bool`, сохраняется максимум старого и нового времени; время до создания диалога отклоняется |
| `.delete(conversation_id)` | Удаление диалога с каскадом сообщений; `bool` |
| `.cleanup_expired(*, now=None)` | Число удалённых диалогов с каскадом сообщений |
| `MessageRepository(connection, ttl_hours=24).append_user_message(session_token_hash, content, *, now=None)` | Один `Message`; проверка сессии, запись и обновление активности одной короткой транзакцией |
| `.append_assistant_message(conversation_id, content, *, now=None)` | Один `Message` отдельной транзакцией для существующего активного диалога; активность не продлевается |
| `.get_history(session_token_hash, *, now=None)` | Кортеж `Message` активного диалога по `created_at, id`; для отсутствующего/истёкшего — пустой кортеж |

Время в публичных методах — `datetime` с часовым поясом. Значение `None`
означает UTC сейчас; перед записью время нормализуется в канонический UTC
`YYYY-MM-DDTHH:MM:SS.ffffffZ`. Наивное время, некорректные UUID/хеши и текст,
пустой после `strip()`, отклоняются. Роли назначаются методами сервера.

В методах записи сообщений текущее время при `now=None` определяется после
получения блокировки `BEGIN IMMEDIATE`: истечение TTL за время ожидания учитывается.
Порядок получения блокировки может отличаться от порядка временных отметок запросов.
Более ранняя отметка сообщения активного диалога не является ошибкой;
`last_activity_at` обновляется атомарным максимумом и никогда не уменьшается.
Ответ ассистента не продлевает активность. Для обеих ролей сохраняется запрет
времени до создания диалога.

`Regulation`, `Product`, `DeliveryPolicy`, `ReturnPolicy`, `Conversation` и
`Message` — неизменяемые типизированные dataclass-результаты. В `Regulation`
доступны `products`, `delivery`, `returns`, `discounts_allowed`. У диалога
есть только хеш токена. Токен из результата `create()` предназначен для будущей
защищённой cookie; его нельзя записывать в логи.

`DatabaseError` сообщает об ошибке версии, структуры или исходного регламента;
инициализация не изменяет такую БД. `SessionUnavailableError` означает
отсутствующую/просроченную сессию или невозможность безопасно обновить активность.
`ValueError` обозначает некорректные параметры методов. Операции репозиториев
могут также сообщать об ошибках `sqlite3.Error`; значения запросов передаются
параметрами, не вставляются в SQL.

`ShopAssistant` уже вызывает `cleanup_expired()`, читает предыдущую историю и
сохраняет запрос через `append_user_message()`. Транзакция завершается до сети.
После классификации обычный ответ сохраняется через `append_assistant_message()`.
Маршрут чата должен использовать сценарий, не дублируя запись пользовательского
запроса. При сбое провайдера запрос остаётся в истории; техническая ошибка не
передаётся как обычный ответ.
Обёртка внешней транзакции вокруг методов `append_*` не нужна и недопустима.

FastAPI и CLI `python -m scripts.init_db` используют одну инициализацию.
Схема, исходные факты и поток данных описаны в [архитектуре](../docs/architecture.md).

При расширении пакета сохраняется направление зависимостей:
`main → assistant → llm/database/schemas`; `llm → schemas`.
`database` не зависит от ассистента и LLM, `config` предоставляет настройки.
Дополнительные слои и пакеты для этих связей не требуются.
