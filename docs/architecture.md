## Реализовано в карточке 06

Python 3.12, FastAPI и Pydantic; настройки через Pydantic Settings.
Uvicorn загружает `app.main:app`. Lifespan вызывает `load_settings()` до
начала обслуживания запросов. Ошибочные настройки прерывают запуск с безопасным
сообщением. Валидированные настройки доступны в `app.state.settings`.

`GET /health` возвращает `HealthResponse(status="ok")`. Других прикладных
маршрутов нет; стандартные `/docs`, `/redoc` и `/openapi.json` предоставляет
FastAPI. Этот endpoint не обращается к DeepSeek и SQLite.

`main.py → config.py` и `main.py → schemas.py` — все текущие прикладные связи.
Реальный код не содержит циклических импортов, классов доступа к данным,
контроллеров или сервисных абстракций. Документация существующего пакета
находится в `app/README.md`.

## Согласованное развитие, ещё не реализовано

Прототип консультирует по регламенту. Он не оформляет заказы, возвраты,
платежи, не имеет интеграции с заказами и не определяет их статусы.
Единственный источник фактов о магазине — утверждённый регламент в SQLite.
Общие знания модели и интернет источниками фактов не служат.

Согласованные файлы остаются в одном пакете `app`:

| Файл | Будущая ответственность |
| --- | --- |
| `main.py` | Валидация HTTP-входа, вызов ассистента и подключение веб-чата |
| `assistant.py` | Координация обработки сообщения, проверка классификации, бизнес-правила и окончательный ответ |
| `llm.py` | DeepSeek, JSON-классификация, таймауты и ограниченные повторы |
| `database.py` | SQLite через стандартный `sqlite3`, регламент, диалоги и аудит изменений |
| `schemas.py` | Pydantic-модели запросов, ответов и классификации |
| `config.py` | Настройки окружения для остальных модулей |

Направление зависимостей: `main → assistant → llm/database/schemas`,
`llm → schemas`. `database` независим от ассистента и LLM; `config` предоставляет
настройки остальным компонентам. ORM и дополнительные слои не вводятся.

Будущий поток сообщения:

1. Браузер передаёт сообщение и cookie непрозрачной анонимной сессии.
2. API валидирует вход; сервер самостоятельно загружает историю из SQLite.
3. DeepSeek определяет намерения и явно названные сущности по необходимому
   контексту. Результат JSON проверяется собственной схемой приложения.
4. Python получает регламент из SQLite, применяет правила и собирает ответ
   из подтверждённых фактов. LLM не формирует окончательный ответ и не решает,
   какие условия магазина действуют.
5. Сервер сохраняет ответ в истории и возвращает его браузеру.

При недостатке данных нужно прямо сообщать об этом или уточнять, не выдумывая
факты. Запрет скидок и правила возвратов должны контролироваться Python-кодом.
История хранится на сервере, срок хранения/неактивности задаётся
`CONVERSATION_TTL_HOURS` (24 часа по умолчанию); механизм сессий и очистки
реализуется отдельной карточкой. Регламент читается без кеширования.
Изменения регламента должны валидироваться и транзакционно записываться
с аудитом доверенным серверным механизмом. SQL будет параметризованным.

Настройки DeepSeek следуют карточке 02: модель `deepseek-flash`,
`https://api.deepseek.com`, таймаут не более 30 секунд и не более двух попыток
на сообщение. При реализации адаптера параметры отключения thinking и JSON
Output потребуется сверить с официальным API. При недоступности провайдера
будет возвращаться техническое сообщение без угадывания ответа и раскрытия
секретов. В этой карточке вызовов API нет.

## Полное дерево и границы каркаса

По явному уточнению пользователя создано полное дерево из карточки 06.
Для отложенных компонентов разрешены файлы с описанием назначения без
реализации будущей логики. `app/assistant.py`, `app/llm.py`, `app/database.py`,
`scripts/init_db.py` и три утверждённых файла будущих тестов содержат только
русскоязычные модульные docstrings. Публичных функций и классов в них пока нет.

`prompts/system.md` и `prompts/classifier.md` описывают назначение будущих
инструкций, но не являются рабочими промптами. `web/index.html`, `web/style.css`
и `web/app.js` содержат только комментарии о назначении; браузерный чат не
реализован и не подключён к API. Скрипт инициализации не содержит исполняемого
кода: его запуск не создаёт SQLite. Фиктивных успешных ответов, тестов,
классов и вызовов провайдера не добавлено.

Рабочие проверки каркаса находятся в дополнительных `tests/test_config.py`,
`tests/test_main.py`; `tests/conftest.py` изолирует их окружение.
Фактическое дерево приведено в главном README и отчёте проверок.

Карточка 03 не утверждает имена таблиц, поля и связи; сама по себе
настройка `SQLITE_PATH` не даёт оснований создавать схему. Регламент не будет
одним неструктурированным блоком: значения должны быть доступны Python
для применения правил. Конкретная группировка записей остаётся в карточке 03.
Тесты ассистента, БД и три краш-теста задания появятся после реализации
соответствующих компонентов; их прохождение сейчас не заявляется.
