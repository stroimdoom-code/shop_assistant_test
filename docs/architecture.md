## Реализовано в карточках 06 и 03

Python 3.12, FastAPI и Pydantic; настройки через Pydantic Settings.
Uvicorn загружает `app.main:app`. Lifespan вызывает `load_settings()`, затем
общую `initialize_database()` в пуле потоков до начала обслуживания запросов.
Ошибочные настройки, структура БД или обязательные факты прерывают запуск.
Валидированные настройки доступны в `app.state.settings`; общее соединение
в состоянии приложения не хранится.

`GET /health` возвращает `HealthResponse(status="ok")`. Других прикладных
маршрутов нет; стандартные `/docs`, `/redoc` и `/openapi.json` предоставляет
FastAPI. Этот endpoint не обращается к DeepSeek и SQLite.

Текущие связи: `main.py → config.py/database.py/schemas.py`,
`scripts/init_db.py → config.py/database.py`. В `database.py` реализованы ровно
три репозитория и функции работы с соединениями и инициализацией. Модуль
не зависит от HTTP API, ассистента или LLM. Публичные интерфейсы описаны
в `app/README.md`.

## Границы и дальнейшее развитие

Прототип консультирует по регламенту. Он не оформляет заказы, возвраты,
платежи, не имеет интеграции с заказами и не определяет их статусы.
Единственный источник фактов о магазине — утверждённый регламент в SQLite.
Общие знания модели и интернет источниками фактов не служат.

Согласованные файлы остаются в одном пакете `app`:

| Файл | Ответственность |
| --- | --- |
| `main.py` | Валидация HTTP-входа, вызов ассистента и подключение веб-чата |
| `assistant.py` | Координация обработки сообщения, проверка классификации, бизнес-правила и окончательный ответ |
| `llm.py` | DeepSeek, JSON-классификация, таймауты и ограниченные повторы |
| `database.py` | Подключение и инициализация через `sqlite3`, чтение регламента и хранение истории |
| `schemas.py` | Pydantic-модели запросов, ответов и классификации |
| `config.py` | Настройки окружения для остальных модулей |

Направление зависимостей: `main → assistant → llm/database/schemas`,
`llm → schemas`. `database` независим от ассистента и LLM; `config` предоставляет
настройки остальным компонентам. ORM и дополнительные слои не вводятся.

Будущий поток сообщения:

1. Браузер передаёт сообщение и cookie непрозрачной анонимной сессии.
2. API валидирует вход. Сервер находит диалог по хешу токена, проверяет TTL до
   чтения истории и сохраняет сообщение пользователя с обновлением активности
   в короткой транзакции.
3. Вне транзакции SQLite DeepSeek определяет намерения и явно названные сущности
   по необходимому контексту. Приложение проверяет результат по схеме.
4. Python получает регламент из SQLite, применяет правила и собирает ответ
   из подтверждённых фактов. LLM не формирует окончательный ответ и не решает,
   какие условия магазина действуют.
5. Сервер сохраняет ответ отдельной короткой транзакцией и возвращает его
   браузеру. При сбое DeepSeek сообщение пользователя остаётся в истории.

При недостатке данных нужно прямо сообщать об этом или уточнять, не выдумывая
факты. Запрет скидок и правила возвратов должны контролироваться Python-кодом.
Регламент читается из SQLite без кеширования. Изменение цены, редактирование
регламента, административный интерфейс и `knowledge_change_log` исключены.

Настройки DeepSeek следуют карточке 02: модель `deepseek-flash`,
`https://api.deepseek.com`, таймаут не более 30 секунд и не более двух попыток
на сообщение. При реализации адаптера параметры отключения thinking и JSON
Output потребуется сверить с официальным API. При недоступности провайдера
будет возвращаться техническое сообщение без угадывания ответа и раскрытия
секретов. В этой карточке вызовов API нет.

## Реализованная схема SQLite v1

| Таблица | Данные |
| --- | --- |
| `products` | Наушники X1, цена в целых рублях, наличие |
| `delivery_policy` | Курьер на следующий день, слот 18:00–21:00 |
| `return_policy` | Обычный возврат за 14 дней, включая вскрытый товар без брака. Деньги на ту же карту за 3 рабочих дня. Для брака предусмотрена экспертиза без обещания немедленной выплаты |
| `store_settings` | Запрет скидок |
| `conversations` | UUID диалога, уникальный SHA-256-хеш токена, время создания и последней активности |
| `messages` | Ссылка на диалог, роль `user` или `assistant`, текст, время создания |

Четыре таблицы регламента независимы. `products` допускает несколько записей.
Три таблицы общих правил допускают по одной записи с `id = 1`. Индексы служат
для поиска просроченных диалогов и чтения истории по `created_at, id`.
Точный SQL и начальные данные приведены в [карточке 03](https://trello.com/c/McJ4Vt4A).

Физические поля соответствуют SQL карточки:

| Таблица | Столбцы |
| --- | --- |
| `products` | `id INTEGER PK`, `name TEXT`, `price_rubles INTEGER`, `is_in_stock INTEGER (0/1)` |
| `delivery_policy` | `id INTEGER PK (=1)`, `delivery_method TEXT`, `delivery_days_offset INTEGER`, `slot_start TEXT`, `slot_end TEXT` |
| `return_policy` | `id INTEGER PK (=1)`, `return_period_days INTEGER`, `refund_method TEXT`, `refund_processing_working_days INTEGER`, `opened_item_without_defect_allowed INTEGER (0/1)`, `defect_accepted_for_expertise INTEGER (0/1)`, `immediate_refund_promised INTEGER (0/1)` |
| `store_settings` | `id INTEGER PK (=1)`, `discounts_allowed INTEGER (0/1)` |
| `conversations` | `id TEXT PK`, `session_token_hash TEXT UNIQUE`, `created_at TEXT`, `last_activity_at TEXT` |
| `messages` | `id INTEGER PK`, `conversation_id TEXT FK → conversations.id ON DELETE CASCADE`, `role TEXT`, `content TEXT`, `created_at TEXT` |

Все значения обязательны согласно DDL. Цены и сроки положительны и целочисленны,
названия и сообщения непустые, слот использует `HH:MM` с началом раньше конца,
роль сообщения — `user` либо `assistant`. Хеш — 64 строчных hex-символа.
Индексы `idx_conversations_last_activity` и `idx_messages_conversation_created`
обслуживают очистку и порядок истории; уникальный индекс хеша создаёт SQLite.

Начальные строки: X1 в наличии за 2490 ₽; курьер, смещение 1 день, слот
18:00–21:00; обычный возврат 14 дней, `same_card`, поступление за 3 рабочих дня,
вскрытый без брака разрешён, брак принимается на экспертизу, немедленная выплата
не обещана; `discounts_allowed=0`. Диалоги и сообщения изначально пусты.

Python при каждом чтении регламента и запуске сверяет все шесть исходных
фактов. SQL-допустимые изменения цены на 2500 или флага скидок на 1 приводят
к `DatabaseError`, а не к восстановлению исходных значений. Дополнительные
корректные товары допускаются; обязательный X1 должен однозначно сохранять
исходные факты. Его числовой id технический и не определяет бизнес-смысл.
Константы исходного регламента используются для загрузки и проверки,
без подстановок при отсутствии данных в SQLite.

Срок 14 дней и поступление денег за 3 рабочих дня относятся к обычному возврату,
включая вскрытый товар без брака. Они не переносятся автоматически на экспертизу.
Тип 14 дней и точка отсчёта, срок/результат экспертизы, количество товара,
статусы заказов, документы и дополнительные условия в БД не придуманы.

При старте FastAPI и в CLI используется одна функция инициализации из
`app/database.py`. Для пустой БД с версией `0` схема, индексы, четыре записи
регламента и `PRAGMA user_version = 1` фиксируются одной транзакцией.
Для версии `1` проверяются структура и обязательный регламент. Повторный запуск
сохраняет данные и историю в пределах TTL. Неподдерживаемая версия, непустая БД
с версией `0` и ошибка проверки приводят к явному отказу без сброса данных.

Инициализация начинает `BEGIN IMMEDIATE` до чтения `user_version`. DDL выполняется
отдельными `execute()`, без неявной фиксации через `executescript()`. Проверяются
ожидаемые определения таблиц и индексов, `quick_check`, внешние ключи,
исходный регламент и каноническое время истории. Форматирование и регистр SQL
вне строковых литералов не меняют результат проверки структуры. Очистка
выполняется только после успешной проверки в той же транзакции. При ошибке
существующая БД сохраняется, включая историю, которая уже истекла по TTL.

На каждом соединении до транзакции включаются `foreign_keys` и
`busy_timeout = 5000`. Запросы параметризованы, соединения отдельные и закрываются
после работы. `ON DELETE CASCADE` удаляет сообщения вместе с диалогом.
Исходный токен хранится в защищённой cookie, в БД используется только его хеш.
Время хранится в UTC с одинаковой точностью. Диалог просрочен, когда
`last_activity_at <= now_utc - TTL`. `CONVERSATION_TTL_HOURS` задаёт срок
неактивности, по умолчанию 24 часа. Физическая очистка выполняется при старте
и обработке запросов чата.

## Полное дерево и границы каркаса

По явному уточнению пользователя создано полное дерево из карточки 06.
Для отложенных компонентов разрешены файлы с описанием назначения без
реализации будущей логики. По актуальному заданию карточки 03 реализованы
`app/database.py`, `scripts/init_db.py`, `tests/test_database.py` и проверки
SQLite в `tests/test_main.py`. Устаревшие ссылки на перенос реализации в другую
карточку заменены фактическим состоянием.

`prompts/system.md` и `prompts/classifier.md` описывают назначение будущих
инструкций, но не являются рабочими промптами. `web/index.html`, `web/style.css`
и `web/app.js` содержат только комментарии о назначении; браузерный чат не
реализован и не подключён к API. `app/assistant.py`, `app/llm.py`,
`tests/test_assistant.py` и `tests/test_security.py` содержат описания будущего
назначения. Вызовов провайдера и маршрута чата пока нет.

Рабочие проверки каркаса находятся в дополнительных `tests/test_config.py`,
`tests/test_main.py`; `tests/conftest.py` изолирует их окружение.
Фактическое дерево приведено в главном README и отчёте проверок.

Тесты БД и запуска API реализованы. Тесты ассистента и три краш-теста задания
будут добавлены в соответствующих карточках; их прохождение не заявляется.

Реализация управления транзакциями следует документации
[Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html) и
[SQLite](https://www.sqlite.org/lang_transaction.html).
