## Реализованное поведение

Чат загружает серверную историю при открытии. Пустая история даёт нейтральное
приветствие; роли визуально различаются. Enter отправляет, Shift+Enter добавляет
строку. Пробельный ввод не отправляется, длина ограничивается 2000 кодовыми
точками Unicode. Проверка пустоты не меняет передаваемый текст. Во время
отправки виден статус ожидания, синхронный ref блокирует повторный POST до
перерисовки React. Поле очищается, переписка прокручивается к концу.

После ошибки POST исходный черновик возвращается, автоматического повтора POST
нет. GET заново читает историю, заменяя экранные сообщения, чтобы показать
сохранённый до сбоя вопрос без дублирования. После успеха история также
синхронизируется на случай смены просроченной сессии. Если GET не удался,
доступна кнопка загрузки, отправка блокируется до синхронизации.

Fetch использует относительные URL и `credentials: "same-origin"`. Код не
читает cookie и не использует localStorage/sessionStorage. API получает только
поле message. Сообщения выводятся текстом через React, без HTML/Markdown,
сторонних скриптов, шрифтов и обхода React-экранирования. Ответы проверяются
до отображения, неизвестные роли/структуры отклоняются; произвольный текст
ошибки сервера не копируется в интерфейс. Экспортируемые функции и компонент
имеют русские JSDoc-комментарии.

FastAPI раздаёт готовые index.html и assets из web/dist. Неизвестные маршруты,
включая `/api/*`, сохраняют 404, health и маршруты API работают как прежде.
Без сборки API запускается, корень возвращает безопасный 503. Сборка должна
предшествовать запуску Uvicorn; в Python wheel фронтенд не упаковывается.

## Реализованный контракт

POST принимает только `{"message":"..."}`: строгая строка длиной до 2000
символов с непробельным содержимым. Исходный текст сохраняется без изменения.
Дополнительные поля запрещены, клиент не может назначить роль или передать
историю. Ответ содержит только `answer` и `created_at`, взятые из сохранённого
сообщения ассистента. GET возвращает полную историю в хронологическом порядке
с полями `role`, `content`, `created_at`; время — UTC. ID и токены в JSON отсутствуют.

Cookie `shop_assistant_session` содержит случайный токен, SQLite — только его
SHA-256. Атрибуты: HttpOnly, SameSite=Lax, Path=/api/chat, без Domain,
Secure при HTTPS и без Secure для локального HTTP. Max-Age определяется TTL
и обновляется при POST. GET не создаёт сессию и не обновляет её активность
или cookie. Недействительная cookie очищается, а POST создаёт новую сессию.
Истёкшие данные удаляются существующим репозиторием с каскадным удалением сообщений.

Ошибки имеют формат `{"error":{"code":"...","message":"..."}}`:
422/invalid_request, 503/service_unavailable, 504/request_timeout,
500/internal_error. Внутренние исключения, SQL, ключи и ошибки валидации
с исходными значениями клиенту не передаются. Уже сохранённый вопрос остаётся
в истории, технический ответ не записывается. Cookie новой сессии возвращается
и при ошибке сервиса, обеспечивая доступ к сохранённому вопросу.
Ответы чата содержат `Cache-Control: no-store`. CORS и streaming отсутствуют.

## Сервисный интерфейс и последовательность

В текущем сервисе не было отдельного результата с временем и различимыми
ошибками: `ShopAssistant.respond()` возвращал техническую строку. Добавлен
`ShopAssistant.process() -> Message` с `AssistantUnavailableError` и
`AssistantTimeoutError`. Совместимый `respond() -> str` сохранён.
Для исчерпанных сетевых/общих таймаутов и HTTP 408/504 адаптер возбуждает
`ClassificationTimeoutError`, подкласс прежнего `ClassificationError`.
Существующие ограничения числа попыток и времени не изменены.

`AssistantService` в том же `app/assistant.py` сериализует весь сценарий одной
сессии. Разные сессии не делят блокировку. Реестр учитывает ожидающие запросы
и очищается после успеха, исключения и отмены. Во время модели SQLite не
удерживается. Один экземпляр сервиса создаётся в lifespan и предоставляется
маршруту заменяемой зависимостью `get_assistant_service()`.
API не читает регламент, не формирует покупательский ответ и не дублирует
запись сообщений. SQL в маршрутах отсутствует.

Для MVP требуется запуск Uvicorn с **одним worker** из-за блокировок в памяти.
Redis и ограничитель запросов не добавлены. README, документация пакета и
архитектура актуализированы. Браузерный интерфейс остаётся отдельной задачей.

# Предыдущий этап: формирование ответов покупателю по регламенту

Проверено 05.11.2026 по [карточке](https://trello.com/c/tJIbbpKh).
Сценарий реализован в `app/assistant.py`, публичный вход —

## Реализованное поведение

Сценарий проверяет активную сессию, выбирает предыдущую историю, атомарно
сохраняет новое пользовательское сообщение с обновлением активности, затем
вызывает классификатор вне соединения и транзакции SQLite. Число предыдущих
сообщений задаёт `CLASSIFIER_CONTEXT_MESSAGES`: по умолчанию 5, значение 0
отключает контекст. Текущее сообщение передаётся отдельно и не дублируется.
Регламент читается и проверяется перед формированием ответа; ответ сохраняется
отдельной операцией. Синхронные операции SQLite выполняются в пуле потоков.

Ответ собирается Python-кодом в порядке тем и запрошенных сведений. Цена и
наличие берутся из каталога SQLite; неизвестная модель и отсутствие сведений
о характеристике обозначаются явно. Общая доставка отделена от неизвестного
статуса заказа 1842. Обычный возврат, вскрытый товар, возврат на 16-й день и
экспертиза брака обрабатываются отдельно. Экспертиза не сопровождается
обещанием немедленного возврата денег, срока или результата. На просьбу
о скидке возвращается «Скидок нет», а при отдельном вопросе о цене — исходная
цена из БД. Сумма со скидкой не вычисляется. Смешанный вопрос сохраняет все

# Исправление параллельной записи сообщений (предыдущий этап)

Проверено 04.11.2026. Исправлены `app/database.py`, `tests/test_database.py`,
`app/README.md`, `docs/architecture.md` и этот отчёт.

Если запрос с отметкой T2 сохранялся раньше ожидавшего запроса с отметкой T1,
где T1 < T2, старый `touch()` отклонял сообщение активной сессии. Ответ ассистента
также отклонялся при времени раньше последней активности. Дополнительно время
для TTL фиксировалось до ожидания блокировки SQLite.

Теперь активность обновляется атомарно как `max(last_activity_at, new_time)`.
Запись с более ранней отметкой допускается для активного диалога, сохраняя
запрет времени до создания диалога. Ответ ассистента не продлевает активность.
При `now=None` время определяется после получения `BEGIN IMMEDIATE`, чтобы
проверка TTL учитывала ожидание блокировки.

Четыре детерминированных регрессионных случая сначала воспроизвели ошибку:
отказ при инверсии временных отметок для обеих ролей и продолжение сессии,
истёкшей за время ожидания. После исправления они прошли. Добавлены ещё два
теста с отдельным потоком и соединением, начинающим запись при удерживаемой
